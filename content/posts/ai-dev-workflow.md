最近看到一篇文章，一位入职大厂两个月的研发讲他怎么用 AI 做日常开发。看完挺有共鸣——他踩过的阶段我基本都走过，有些结论是用我自己的代价换来的。这篇不是翻译，是把其中有用的几条主线拆出来，加上我自己的理解和经历，重新讲一遍。原文出处放在最后。

## 一、工具的关键是分工，不是数量

他的用法是每个工具只干一件事：

| 角色 | 用法 |
| --- | --- |
| 编码主力 | 核心代码落地、测试先行、增量拆解 |
| 宏观规划 | 复杂需求的前期方案和架构梳理 |
| 轻量杂活 | 脚本、小改动、快速排障，图快图便宜 |
| 对抗审查 | 专门的挑刺角色，找假设漏洞和逻辑死角 |

我对「对抗审查」这一条感触最深。让写代码的 Agent 自己审自己，基本等于没审——它不会轻易推翻自己刚才的决策。换个模型、换个会话来审，效果完全不一样，我自己排查问题时也反复验证了这一点：**换一个不知情的视角，比同一个视角多想十轮都管用。**

他还有个经验：任何重复超过三次的自测或排障流程，就固化成脚本或 Skill。这个我举双手同意。我自己搭这个博客时，字体子集化、本地预览、构建验证这些事，第一次做是研究，第三次做就必须是命令。

## 二、把方法论写成「思维快捷键」

他很少写几百行的复杂 Prompt，而是直接用一句话点名一套成熟方法论，让模型自己调用。核心就五个：

**第一性原理——先怀疑方向，再优化参数。**

> 不要基于「加缓存」这个既定方案继续设计，分析它为什么慢，最小必要的解是什么。

用来防止模型在你给的错误方向上精雕细琢。很多时候瓶颈根本不在你以为的地方。

**对抗性审查——不许找理由，只许找反例。**

> 对这个方案做对抗性审查，优先找能推翻核心假设的反例。

这一条治的是「模型倾向于同意你」。明确要求它站到对立面，它才会认真。

**消融实验——系统变好，不代表你加的每项都有用。**

> 给这几个优化设计消融实验，判断收益分别来自哪里。

三个改动一起上，耗时从 800ms 降到 120ms，很可能其中一项贡献了 100ms，另外两项是心理安慰。不拆开测，你就会一直养着没用的复杂度。

**奥卡姆剃刀——满足需求的前提下，删掉所有非必要机制。**

模型（和我自己）都有个毛病：爱为假想的未来设计。状态机、抽象层、配置化，一层层垒上去，Review 的人看得头皮发麻。定期问一句「没有它行不行」，能砍掉一大半。

**高内聚低耦合——查职责边界，不为拆而拆。**

拆模块是好事，但为了拆而拆只是把耦合从代码里挪到了接口文档里。

这五个可以组合成一句总指令用：重新定义问题、攻击假设、验证贡献、删除复杂度、整理边界。

## 三、工作流：先对齐，再小步验收

他分成两个阶段，我觉得这个切分本身就是对的：

**阶段一，对齐。** 把 PRD、会议纪要、用户反馈一股脑丢给 Agent 通读，再让它扮演资深架构师连续追问，把目标、边界、取舍逼出来。关键在尺度：**剩下的问题已经不会改变实现方向和验收结果时，就果断开始做。** 对齐本身也会变成过度设计——我见过太多时间花在「方案无限细化」上，一行代码没写。

对齐的结论要落成文档，后面并行的 Agent 直接共享，不用每个人都重读一遍长对话。

**阶段二，小增量闭环。** 主 Agent 拆需求，能独立推进的派给子 Agent 在独立 worktree 并行做，写完交叉审查，最后端到端测试加人工过一遍核心逻辑。每一步都保持「一个小 MR」——这是我最认同的一条。大 MR 是 Review 质量的坟墓，这个道理不用 AI 时代也成立。

## 四、给 Agent 一个能自证的环境

这条是他文章里我最想照做的部分。AI 写单测已经很猛了，但上线还是崩，原因是单测跑在真空中：Agent 自测通过，不代表它在真实系统里能跑通。

他认为 Harness 要解决四件事：

1. **环境一键可得**——沙盒、测试数据、版本权限，说拉就拉，用完能重置。
2. **能操作真实业务系统**——通过浏览器、API 或 CLI 走完整业务流程，而不是只调函数。
3. **能查库查日志**——只读权限验证落库状态，顺着日志追全链路。
4. **稳定的流程固化成 CLI**——环境检测、数据准备、场景执行、清理，收进一个内部测试命令行。

还有一点他专门强调了，我原文照搬一个意思：**工具给你的是证据，不是答案。** 数据库返回 200、日志没有异常，都不等于业务做对了——系统完全可能「看似合理地返回一个违背业务常识的值」。预期结果必须来自业务契约本身。

这一点我太有切身体会了。我给博客做中文字体子集化，脚本跑完退出码是 0，产物也生成了——但产物是个 31KB 的空壳字体，满屏汉字全是错的。工具安静地执行了错误指令，一个警告都没给。从那以后我给自己定了一条规矩：**凡是结果可验证的，流程末尾就必须验证一次。** 跑完反查字形数量，改完 JSON 先解析一遍。把「沉默地错」变成「大声地错」，这是 Harness 该干的事。

如果被测系统自己就是 Agent，那还得加一层：除了流程跑通，输出质量也要有评测。

## 五、Review 的重心：抓高危，放过 CRUD

他的四条 Review 原则，我压缩成两句话：

**先看验收标准和测试证据，再看代码。** 重点不是「测试全绿」，而是「测试到底测了什么」——为了通过测试而写出迎合错误实现的断言，是 AI 的常规操作。

**精力花在会出事的地方。** 权限校验、状态迁移、并发竞争、失败重试、数据一致性、数据库 Migration 和回滚，这些逐个看；模式固定的单表 CRUD，他说他现在完全不看，我基本同意。另外，看到新增的工厂类、泛型适配器、冗长状态机，直接上奥卡姆剃刀。

## 六、真正的瓶颈是人，不是 AI

他的结论我很认同：现在的瓶颈早就不是编码速度，而是**人工 Review 的吞吐上限**。Agent 能并行推三个需求，但人理解业务、权衡边界、验收交付的心智带宽就那么多。一味让 AI 多写，最后只会堆出一座没人敢碰的审查堰塞湖。

所以他给 Harness 的定义是：除了正确的上下文，还要有**能执行任务的真实环境**和**判断对错的物理证据**——跟第四点呼应上了。

还有两条个人习惯：

**定期给工作流做减法。** 很多规则是当年给模型短板打的补丁，模型换代之后这些约束就变成了干扰噪声。他提到 OpenAI 发新模型时专门写博客讲怎么清理 Skill 和系统提示词，说明这不是他一个人的观察。`AGENTS.md` 也该定期除草。

**给自己留出踩坑的时间。** AI 确实拿走了一部分亲手排障的机会——以前是痛苦地 debug，现在是听它说一句「我错了，马上改」。不亲手踩坑，判断力是会退化的。他每天固定留时间学领域深水区的知识，我觉得这个习惯比任何工具都保值。

## 起步建议

别想着一步到位搭个全自动框架。挑一条你最常做的本地自测路径，让 Agent 独立跑通、留下证据，把有效步骤写成脚本——你的个人 Harness 就算开始了。

我自己下一步打算做的，就是把博客这个项目当成试验田：构建、预览、字体子集化、链接检查，全部收进一个脚本，让 Agent 能自己跑完自己验。
