## 一次差点放过的错误

给博客做中文字体子集化，脚本跑完没报错，产物也确实生成了。

但打开浏览器一看，字全变了形。查字体文件大小——**31KB**。

源字体 16.9MB，6763 个汉字的子集怎么可能只有 31KB。脚本里的字表命令是：

```bash
pyftsubset font.ttf --unicodes-file=charset.txt
```

而 `charset.txt` 里写的是十进制数字。`fontTools` 不认识这个格式，**读出一个空字符集**，于是安静地生成了一个几乎空的字体。没有警告，没有非零退出码，命令行返回一切正常。

正确的写法是 `U+XXXX`：

```python
charset_file.write_text("\n".join(f"U+{ord(c):04X}" for c in chars))
```

改完之后产物是 1839KB，用 `fontTools` 反查字形数量确认是 6763 个汉字，才算真的对。

一个参数格式写错，工具不会报错——它只会忠实地执行你给的错误指令。

当时的第一反应也不是「字表格式可能有问题」，而是「字体是不是没生效」。
毕竟整个站点的中文都靠这一个字体撑着，它一旦不对，症状就是满屏的字都不对。

这种时候最容易犯的错，是顺着「字体」这个方向一路查下去：
文件在不在、`@font-face` 写没写、路径对不对、MIME 类型对不对。
每一项单看都是合理的怀疑，但没有一项是真正的原因。

真正定位问题的动作，是去查那个产物的**规模**——31KB 对应 6763 个汉字，
这个数量级本身就不可能成立。凡是结果「看起来对」的时候，
先确认它的量级对不对，往往比逐项排查更快。

## 为什么静默失败比崩溃贵

崩溃是好事。它在第一时间告诉你「这里不对」，而且往往直接指向原因。

静默失败不一样。它让你在一个错误的前提下继续往前走——继续写代码、继续跑测试、继续往下走——等到问题浮出水面时，已经积累了大量基于错误前提的产物。

更麻烦的是它会**污染判断**。你不会怀疑一个刚跑通的命令，你会怀疑别的地方。这个博客搭好之前，「所有 CSS 请求 404」这个现象把我引到了完全错误的方向上：

实际原因是端口被一个僵尸 `hugo` 进程占着，它在响应，但响应的是几个星期前的旧产物。

如果当时继续去查 `hugo.toml` 里的资源引用、SCSS 编译规则，能查到天亮也找不出来。

## 我踩过的几类

### 配置读到了但没生效

`defaultContentLanguage` 写成了 `zh`，而主题的翻译文件叫 `zh-cn.toml`。结果是所有界面文案变成空白，**构建成功，没有任何警告**。

配置类问题的共同点是：值确实被读进去了，只是不匹配。Hugo 不会检查「这个语言码有没有对应的翻译文件」。

同类还有：

- `buildFuture` 默认 `false`，日期写成明天的文章被静默排除，不报错也不显示
- `baseURL` 写错时构建能过，但全站链接 404

这些的共同解法是：**改完配置一定要在浏览器里点一遍**。构建成功不等于配置生效。

### 改对了元素，但没生效

中文显示「怪怪的」，我第一反应是字体。查了一圈发现不是——是字距。

主题给导航标题设了 `letter-spacing: 0.1rem`。这个值对拉丁字母是有用的，但用在汉字上，每个字之间会被硬生生撑开一道缝，看起来像挤在一起又散着。

我改的是 `.post-title h1`，可正文的样式写在 `.post-title .title` 上，选择器根本对不上。

还有一次是自定义 SCSS 覆盖不生效：我写 `.navigation-title { ... }`，主题写的是 `.navigation .navigation-title`。后者特异性更高，加载顺序在后面也救不了——**CSS 的加载顺序弥补不了特异性的差距**。

### 权限被收窄成 none

CI 报缓存写入失败。查下来是 workflow 里写了：

```yaml
permissions:
  contents: read
  pages: write
  id-token: write
```

显式列举的语义是**没列出来的全部置为 none**。所以 `actions: write` 实际是关闭的，`peaceiris/actions-hugo` 的缓存步骤必然失败。

修法是加 `cache-disable: true`，而不是去补权限——runner 每次都是全新环境，缓存本来也用不上。

### 工具调用本身是错的

这个博客的 CI 第一次失败是因为我写了一个不存在的 action：

```
Error: Unable to resolve action actions/setup-hugo, repository not found
```

这个错误至少是诚实的，它直接点出了「action 不存在」。真正需要警惕的是相反的情况：**看起来合理、实际不存在的东西，凭空被写了出来**，然后要等到运行时才发现。

所以现在我养成了一个习惯：凡是引用外部 action、参数名、API 字段，先查一遍再写。凭印象写出来的东西，出错时机是不可控的。

## 怎么防

收集下来的经验其实很朴素：

**失败要响。** 能在工具里加断言就加。子集化完反查一次字形数量，写完 JSON 解析一次合法性。工具不报错不代表结果对，但你可以让它必须能回答「你要的东西真的在这里吗」。

**换一个工具交叉验证。** `fontTools` 能告诉你字形数量，浏览器能告诉你字体有没有真的用上。单一来源的验证容易被同一个 bug 骗两次。

**先确认现象，再动手改。** 那个 CSS 404 的教训是：我当时没先确认端口上跑的是谁。`Stop-Process` 加 `Get-Process` 一起做，五秒钟解决的事，绕了半小时。

**区分「没报错」和「是对的」。** 这是最容易省掉、也最贵的一步。

## 目前在做的事

谈不上体系化，主要是几条从反复踩坑里长出来的习惯：

写脚本的时候，只要结果是可验证的，就在末尾加一次验证。
字体子集化跑完，用 `fontTools` 反查字形数量；改完 JSON，先 `json.loads` 一次。
这些检查花几秒钟，但能把「沉默地错」变成「大声地错」。

改配置之后，一定在浏览器里点一遍首页和一个列表页。
这半年花在静态站点上的时间，有一大半本来是花在「改完了但不知道生效没有」上的。

CI 报错时，先读完整个日志再动手。看到 `caches must resolve to an absolute directory`，
第一反应不该是「缓存路径要怎么写」，而是「为什么我这里需要指定缓存路径」。
真正的原因是我加了一个不必要的配置——读日志能省掉很多猜测。

至于「工具调用本身是错的」这一类，现在的做法是：凡是引用外部 action、参数名、API 字段，
先查一遍再写。凭印象写出来的东西，出错时机完全不可控。

## 最后

静默失败本质上不是技术问题，是**反馈缺失**的问题。

它不会让你变聪明，只会让错误停留得更久一点。

所以我现在对「一切正常」这两个字的警惕，比对报错的警惕还高。
